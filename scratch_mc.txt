
MASTER CONTEXT 
You are helping build a systematic crypto trading research system. Before writing any code, internalize these constraints. They are not suggestions — violating them makes the output unusable regardless of how well it otherwise works.
Design philosophy
The central metric is Expected Value per trade, not win rate or accuracy. Priority order: capital preservation &gt; risk-adjusted returns &gt; robustness across regimes &gt; adaptability (detecting when the system stops working) &gt; raw prediction accuracy.
The single edge hypothesis being tested
Post-compression liquidity-sweep reversals in BTC and ETH on the 1H–4H timeframe, during risk-on macro regimes, with multi-timeframe structural alignment, carry positive expected value after costs, with minimum Sharpe 1.0 over a minimum 200-trade out-of-sample sample. Everything in this system exists to test or protect this hypothesis. Nothing else.
Non-negotiable global constraints
Temporal partitioning is physical, not conventional. Training, validation, and test data live in separate, immutable partitions. Code in one partition must not access data from a later partition, even accidentally. Every feature must be calculable using only data available at that exact timestamp — no forward-looking windows, ever.
No lookahead bias, anywhere. Every rolling/percentile calculation uses only closed candles up to and including the current timestamp. This is the single most important rule in the whole project.
Raw and normalized data are stored separately. Raw is never overwritten. Normalized data is always reproducible from raw.
Walk-forward validation only. Train → validate → test, rolling forward, never overlapping. Hyperparameters and ensemble weights are tuned on the validation fold only, never the training fold, never the test fold.
Ensemble Meta-Model is linear only. A weighted average with learned weights. No non-linear stacking, no secondary model at this layer.
Kelly sizing is hard-capped at 0.25 (quarter-Kelly), and is overridden unconditionally by: max 2% single-trade risk, max 6% correlated-direction risk, max 10% aggregate open risk. These three numbers are enforced at the execution layer independent of any model output.
EV threshold uses the lower confidence-interval bound, not the point estimate. Minimum: EV lower CI bound &gt; +0.15% per unit risk.
Six trade-entry gates must all pass simultaneously: EV lower CI bound &gt; +0.15%; MTF alignment ≥ 3/4; macro regime is Risk-On or Transitional; volatility regime is not Spike; analog sample size ≥ 50 independent instances; risk score ≤ 65/100.
Minimum sample gate for the k-NN analog engine: N ≥ 50 independent instances, with overlapping-window instances from the same directional move counted as one, not many.
Two separate gate systems — do not conflate these
There are two distinct threshold sets in this spec, used at different points. Mixing them up is a real failure mode, so keep them explicitly separate in code and in any reporting output.
A. Layer 14 research-phase kill criteria (used during Phase 1/2 backtesting to decide continue-vs-revise-the-hypothesis):
Out-of-sample Sharpe &lt; 0.5 → stop, revise hypothesis
Out-of-sample profit factor &lt; 1.2 → stop, revise hypothesis
Out-of-sample max drawdown &gt; 25% → stop, revise risk engine
Risk-On regime performance worse than aggregate performance → macro conditioning isn't working, remove and retest simpler hypothesis
Ensemble weight instability across &gt; 2 consecutive folds → unreliable, fall back to equal weighting and investigate
